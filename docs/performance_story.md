| 阶段 | 配置 | QPS | 每请求 CPU | 关键动作 |
|---|---|---|---|---|

## 1. 第 0 轮：起点

**现象**：简历/README 写 48,442 QPS、p99 382 µs。

**当时的口径**：8 线程、8 条长连接、每个线程发一个请求等回来再发下一个。

---

## 2. 第 1 轮：发现"这个数字是测出来的，不是做出来的"

### 怎么发现的

**读代码**（`tests/test_benchmark.cc:59-69`）：

```cpp
auto future = client.asyncCall(...);
auto resp   = future.get();      // ← 发一个，等一个
```

**拿 README 的数据反解**：

| 线程 | QPS | 反解 RTT = 线程数 ÷ QPS |
|---|---|---|
| 1 | 11,842 | 84.4 µs |
| 2 | 19,795 | 101.0 µs |
| 4 | 34,397 | 116.3 µs |
| 8 | 48,442 | 165.1 µs |

### 结论

```
QPS = 在途请求数 ÷ RTT
```
每个线程同时只有 1 个请求在飞，所以在途数 = 线程数 = 8。
**4.8 万不是框架上限，是"8 个在途请求"的上限。**

---

## 3. 第 2 轮：服务端真的只开了一个 Reactor

### 怎么发现的

**读代码**：
- `src/network/event_loop_thread_pool.cc:12`：`numThreads_(0)`
- `:38-50`：`loops_` 为空时 `getNextLoop()` 恒返回 `baseLoop_`
- `grep setThreadNum` → 全项目**零调用**

### 做了什么

```cpp
// src/server/rpc_server.h —— 补一个转发（原来只有 TcpServer 有）
void setThreadNum(int n) { server_.setThreadNum(n); }

// examples/rpc/rpc_server_main.cc —— 必须在 start() 之前
server.setThreadNum(4);
```

> 踩坑：`setThreadNum` 在 `start()` 之后调用**不报错也不生效**。

### 结果

| 配置 | QPS | p99 |
|---|---|---|
| 单 Reactor | 56,047 | 626 µs |
| 4 从 Reactor | **61,683** | **461 µs** |

**+10%——远低于预期。**

---

## 4. 第 3 轮：两个假设被证伪

### 假设 A：服务端并行度不够

**方法**：benchmark 加参数，单变量 A/B（8 连接，2 万请求）。

| 从 Reactor | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| QPS | 51,240 | 55,224 | 57,111 | 61,901 |

**8 倍线程只换来 1.21 倍吞吐 → 证伪。**

### 假设 B：每请求超时定时器是大头

**方法**：`timeout_ms=0` 时 `doCall` 里的 `if (timeout_ms > 0)` 不成立，定时器完全不注册。

| 超时 | QPS |
|---|---|
| 3000 ms | 57,771 |
| 0 | 58,594 |

**+1.4% → 证伪。**

> 面试要点：**两个最自信的假设都错了**，这比任何优化都更能证明会做实验。

---

## 5. 第 4 轮：用 strace 找到真因

### 命令

```bash
strace -c -f -e trace=write,read,readv,epoll_wait,futex,eventfd2 \
  ./test_benchmark 2000 4 8 3000 only
```

### 结果（8,000 请求）

| syscall | 每请求 | 在干什么 |
|---|---|---|
| futex | 4.03 | promise 的睡眠/唤醒 |
| write | 4.02 | 2 次 eventfd + 2 次 socket |
| epoll_wait | 3.05 | 两端 |
| readv | 2.00 | 收数据 |
| read | 1.04 | 读 eventfd |
| **合计** | **14.15** | |

### 判断

**只有 4 次在真正传数据（2 readv + 2 socket write），7 次是"把请求从一个线程搬到另一个线程"。**

配合 `/usr/bin/time`：`user 1.45s : sys 6.04s` —— **80% 时间在内核态**。

---

## 6. 第 5 轮：先把测量改对（流水线）

### 怎么发现的

**读代码**（`rpc_async_client.cc:392-435`）：Future 版 `asyncCall` 返回前就 `future.get()` 了——**伪异步**，同一个线程没法连发。

### 做了什么

新写 `tests/bench_pipeline.cc`：用**回调 API**，每连接维持 64 个在途请求。

> 关键约束：`handleResponse` 是**持锁**调回调的，所以回调里不能再 `asyncCall`（会死锁）→ 用独立提交线程 + 条件变量补发。

### 结果

**101 万 QPS**（8 连接 × 64 在途，1000 万请求，4 从 Reactor）。
**这一步一行框架代码都没改**，只是换了测量方式。

---

## 7. 第 6 轮：调用线程驱动 IO（真正改实现）

### 怎么发现的

**读代码**：
- `TcpConnection::send` 跨线程时走 `runInLoop` → `queueInLoop` → **`write(eventfd)`**
- `EventLoop::runAfter` 跨线程时同样 **`write(eventfd)`**
- `future.get()` 阻塞 → futex

### 做了什么

1. `EventLoop::loopOnce()`：把 `loop()` 拆成"跑一轮事件"；
2. 新增 `InlineSyncClient`：`EventLoop` 构造在调用线程，`send` 直接 `write`，等响应就在本线程 `loopOnce`；
3. 超时不用定时器，把剩余时间交给 `epoll_wait`。

### 结果（同口径：闭环、8 线程、5 万请求）

| 指标 | 改前 | 改后 |
|---|---|---|
| 系统调用/请求 | 14.15 | **6.06** |
| futex/请求 | 4.03 | **0.01** |
| 每请求 CPU | 93.6 µs | **46.7 µs** |
| QPS | 61,683 | **131,996** |
| p99 | 461 µs | **180 µs** |

**2.14×，p99 −61%。**

---

## 8. 第 7 轮：两个优化叠加

### 为什么能叠

- 流水线解决"**在途数**"（并发度）；
- 调用线程驱动解决"**每请求成本**"；
- 两者正交。

### 做了什么

新增 `InlinePipelineClient`：
- 一个线程既提交又驱动 loop；
- `pending_` 表**线程私有，无锁**；
- 无 eventfd、无每请求定时器（deadline 交给 `epoll_wait`）。

### 结果

**162 万 QPS**（16 连接 × 64 在途，4 从 Reactor，1000 万请求）。

---

## 9. 第 8 轮：服务端 Reactor 饱和

### 怎么发现的

**`top -H`** 采样：**4 个线程 99.9%，客户端线程只有 33~40%**。

### 结果

| 从 Reactor | QPS | CPU |
|---|---|---|
| 4 | 161.8 万 | 8.4 核 |
| 8 | 203.8 万 | 11.9 核 |
| 12 | 212.0 万 | 11.1 核 |
| **16** | **264.9 万** | 12.8 核 |
| 20 | 267.9 万 | 12.7 核 |

**16 个之后不再涨。**

## 10. 第 9 轮：加连接反而降 → CPU 打满

| 连接数（16 Reactor） | QPS | avg |
|---|---|---|
| **16** | **270.3 万** | 249 µs |
| 24 | 248.6 万 | 458 µs |
| 32 | 257.4 万 | 624 µs |
| 48 | 239.4 万 | 1067 µs |

**加并发不涨反降 = CPU 打满后只增加排队。**

⚠️ 口径修正：这台机器是 **6P + 4E = 10 物理核 / 16 逻辑核**。
syscall 密集型负载吃不满超线程，**12.5 逻辑核 ≈ 实际上限**。
所以"CPU 只用了 78%、还有余量"是误导。

## 11. 第 10 轮：排除上下文切换

**命令**：

```bash
/usr/bin/time -v ./bench_inline_pipeline 16 64 2000000 12
vmstat 1 3
```

**结果（200 万请求）**：

| 指标 | 数值 | 换算 |
|---|---|---|
| 主动切换 | 76,205 | 每 100 请求 3.8 次 |
| 被动切换 | 27,665 | 每 100 请求 1.4 次 |
| 合计 | ~104k | **每请求 0.05 次**（约占总 CPU 2~3%） |

`vmstat` 的 `r`（就绪线程数）实测 **9 / 1**，远小于 16。

> **线程数 > 核数 ≠ 切换灾难**：大量线程睡在 `epoll_wait` 里，不参与调度。

## 12. 期间修掉的真 bug（都是"顺带"发现的）

| # | Bug | 怎么发现的 | 修复 |
|---|---|---|---|
| 1 | 连接池把同一条连接给两个客户端 → 响应串包 | 压测 8 线程 / 4 连接出现 4 errors + 卡 3.00s | `TcpClient` 所有权声明（CAS） |
| 2 | 三个 use-after-free | 偶发 segfault，**ASan 下 1/1 必现** | `Channel::tie` 保活、Connector 延迟销毁 Channel、回调改 `weak_ptr` |
| 3 | `TCP_NODELAY` 让流水线吞吐 −30% | 复查 101 万时变成 76 万 → 旧提交同机对比排除降频 → 二分 → 临时关掉验证 | 改成可配置、默认关闭 |
| 4 | `~EventLoop` 析构 abort | 压测 `signal 6`，gdb 栈指向 `~Channel → removeChannel → assertInLoopThread` | 析构时先清 `pendingFunctors_`/`timers_` |

**第 3 条最有价值**："看起来更专业"的改动，让吞吐掉了 30%。

## 13. 当前瓶颈与优化方向

### 现在的瓶颈

- 上限 **约 265~270 万 QPS**；
- CPU **12.5 / 16 逻辑核**（≈10 物理核，已贴墙）；
- 每请求 **5.3~5.9 µs** CPU，其中：
  - **sys 约 55%**：2.6 次系统调用（2 次 `write` 是大头）
  - **user 约 45%**：protobuf 4 次操作 + 多次拷贝

### 优化方向

| 优先级 | 动作 | 砍掉什么 | 预期 |
|---|---|---|---|
| P0 | 服务端**批量写**（每轮 `writev`） | 每请求 2 次 write → ~1.1 次 | +10~15% |
| P1 | 协议瘦身：method id、去嵌套 payload、`ParseFromArray` | 4 次 protobuf + 3~4 次拷贝 | +10~15% |
| P2 | 内存池 / arena | 十几 allocs/请求 | +5~10% |
| P3 | 业务挪线程池 | 让 IO 线程只做收发 | 稳定性，不是吞吐 |
| P4 | 多机 / `io_uring` / 共享内存 | 突破单机边界 | 数量级 |

## 14. 方法论：四步法（最值得讲的部分）

```
① 测准 —— 先确认你测的是什么（口径、在途数、延迟还是吞吐）
② 证伪 —— 提假设，单变量 A/B，看边际收益
③ 量化 —— strace 数系统调用、/usr/bin/time 看 user/sys、top -H 看线程
④ 验证 —— 改一处、同套基准复测、回归测试（含 ASan）
```

### 工具速查

| 想回答什么 | 命令 |
|---|---|
| 每请求几次系统调用 | `strace -c -f -e trace=write,readv,epoll_wait,futex ./prog` |
| CPU 花在用户态还是内核态 | `/usr/bin/time -v ./prog` |
| 哪个线程在打满 | `top -H -p <pid>` |
| 是否被抢占、就绪队列多长 | `vmstat 1`（看 `r` 和 `cs`） |
| 有没有内存错误 | ASan 构建后跑测试 |
| 延迟分布 | 基准里的 p50/p99/p999 |

## 15. 高频追问与回答

| 追问 | 回答 |
|---|---|
| **"270 万怎么保证不是空转？"** | `Errors: 0`、`Done == 总数`；服务端真的解析+序列化；**用了 12.5 个逻辑核**——空转烧不掉 |
| **"为什么闭环只有 6 万？"** | `QPS = 在途数 / RTT`，闭环在途=线程数=8，所以 6 万本质是 128µs 的往返延迟 |
| **"101 万和 270 万差在哪？"** | 101 万是跨线程流水线；270 万 = 单线程流水线（每请求 13→5.3µs）+ 16 个 Reactor |
| **"有没有踩坑？"** | TCP_NODELAY 让吞吐掉 30%，靠旧提交同机对比 + 二分定位，最后改成可配置默认关 |
| **"最大的收获？"** | 不是 270 万这个数，而是"先测准、再改对"这套方法 |
| **"还有什么不足？"** | 伪异步 Future、无 streaming/鉴权、一连接一线程、业务在 IO 线程、无背压 |

## 16. 一分钟版本

> "这个项目我从 4.8 万 QPS 做到了 270 万，但其中 16 倍不是优化出来的，是**之前测错了**。
>
> 原来的压测是发一个等一个，在途数等于线程数，所以 4.8 万本质是 165 微秒的延迟。改成流水线后，同一份代码跑到 101 万。
>
> 然后找瓶颈：我先猜服务端 Reactor 不够、又猜定时器开销大，A/B 一做，一个只提升 21%、一个只提升 1.4%，**两个假设都错了**。用 strace 数系统调用才发现，每请求 14 次里 7 次是线程间搬运。
>
> 于是把同步调用改成调用线程自己驱动 IO，系统调用降到 6 次，同口径吞吐 2.14 倍。再把流水线叠上去，配合服务端 16 个 Reactor，到 270 万。
>
> 现在瓶颈是 CPU：每请求还有 5.3 微秒，一半在内核。下一步是批量写和协议瘦身。"
